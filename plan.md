# Storybook integration: seven components with meaningful tests

## Summary

Integrate Storybook into the existing Minesweeper repository, using its real components and styling. Deliver seven documented components, interactive examples, automated interaction and accessibility checks, a public GitHub Pages site, and an interview walkthrough.

Repository baseline: Next.js 16.1.1, React 18.3.1, Vitest 4.1.10; 21 unit tests and TypeScript checking pass. Lint reports 19 warnings and no errors. Preserve the user's uncommitted AGENTS.md change.

## Architecture and interfaces

- Use Storybook 10.6.5 with @storybook/nextjs-vite and its documentation, accessibility, and Vitest addons. Keep Storybook versions aligned and Vitest browser packages on 4.1.10. Use npm and the existing lockfile; retain application framework versions. All additions are development dependencies.
- Put typed CSF 3 stories beside their components, using Meta, StoryObj, and satisfies. Group the sidebar into UI, Game, and Lobby. Add one introduction page and autogenerated component documentation.
- Import existing SCSS and assets. Override application body layout only in Storybook to avoid clipping documentation. Supply the cell-size CSS variable.
- Replace the settings module only in Storybook with a typed in-memory substitute using fixed defaults, including zoom 1. Keep real selectors and rendering; never initialize production storage subscriptions.
- Use fixed sample boards, dates, and saved-game data. Reset examples and callback records between tests. Do not mount the application layout, account provider, analytics, or database connections.
- Add getAssetUrl() for the four cell-icon components. Keep root-relative application URLs and inject /react-minesweeper only for the Pages build, without adding a required application environment variable.
- Make Button forward its native reference and connect the saved-game confirmation opener through Radix's dialog trigger for focus restoration. Include other targeted fixes demonstrated by tests.
- Add storybook, build-storybook, and test:storybook commands. Separate Vitest into unit and storybook projects, preserving npm test as the unit suite. Storybook uses Chromium through Playwright; full-application browser tests remain separate.

## Phased implementation and acceptance

### 1. Foundation

Save this plan; preserve AGENTS.md; update main; create feature/storybook-portfolio. Add Storybook, styles, assets, settings isolation, and browser tests. Type-check configuration and ignore generated output. Prove the setup with a real Button story and assertion.

Accepted when the server, static build, and browser test work without account/database credentials, and unit tests remain independent.

### 2. Interactive primitives

Complete Button, Switch, and ToggleGroup stories, autogenerated docs, controls, and callback spies. Use example wrappers that update real props and react to Controls changes. Add mouse, keyboard, and disabled-state assertions.

Accepted when documentation and interactions work and tests pass in Storybook and the command line.

### 3. Minesweeper examples

Complete Cell, LevelCard, ContinueBanner, and ScoreSyncNotice. Reuse difficulty definitions and GameSnapshotV1. Implement asset paths and dialog improvements. Simulate retries without account requests. Query the story document body for portalled dialogs.

Accepted when examples remain reproducible after switching or reloading, tests pass, and application preferences are neither read nor written.

### 4. Accessibility and regression checks

Set parameters.a11y.test to error. Include ordinary and open-dialog states; retain an open-dialog story for scanning. Explicitly check keyboard focus, Escape, accessible names, and disabled states. Inspect desktop and narrow layouts and review checks requiring human judgement. Fix issues without broad refactors or disabling checks to pass.

Accepted when stories, interaction/accessibility tests, repeat runs, existing unit/browser tests, type checking, and the application build pass, with no new lint warnings/errors.

### 5. Publish and walkthrough

Review legal pages for the hosting provider and update dates only when their content changes. Update README commands, public URL, check status, and strongest examples. Explain controls, isolation, dialogs, retries, accessibility limits, and component versus full-game testing.

Accepted when the public site needs no sign-in, direct links survive refresh, controls and images work, and failing checks prevent publication.
